# 公众号 AI Studio 2.1.4 代码审计报告

**审计日期**：2026-07-26  
**审计对象**：2.1.3 审计修复源码版（含 2.1.4 日志可观测性增量代码）  
**审计范围**：安全维度、业务逻辑维度、代码质量维度  

---

## 一、审计结论

本轮审计共发现 **7 个高危、15 个中危、12 个低危** 问题，覆盖认证授权、SSRF 防护、SQL 注入、XSS、密钥保护、工作流状态机、乐观锁并发、发布流程、事务完整性、异常处理、资源管理、代码重复与类型安全等方面。

SQL 注入防护和路径遍历防护已做到位，全部使用参数化查询。高危问题集中在以下四个领域：

- **测试适配器可被生产环境滥用**：源码版包含 `.test-adapters-enabled` 标记文件，仅需设置两个环境变量即可绕过 AI/微信/内容安全全部校验
- **发布流程缺乏分布式事务保护**：微信草稿创建后若本地 DB 写入失败，产生不可见的孤儿草稿
- **`_finish_error` 跨三个独立事务**：部分提交导致任务与项目状态不一致
- **`preserve_body` 重试模式语义割裂**：重新生成框架但保留旧正文，框架与正文不匹配

## 二、安全维度审计

### 2.1 认证与授权

#### [高] 测试适配器标记文件可被生产环境滥用

- **文件**：`.test-adapters-enabled`、`backend/test_mode.py:6-19`
- **问题**：当前源码版包含空的 `.test-adapters-enabled` 标记文件。`test_mode.enabled()` 需同时满足三个条件：文件存在（源码版满足）、`STUDIO_ENABLE_TEST_ADAPTERS=1`、特定适配器变量（如 `STUDIO_TEST_AI=1`）。一旦激活，AI 验证返回虚假成功，微信发布写入虚假回执，内容安全检测被跳过。运行包通过 `build_release.py` 排除此文件，但源码版直接部署时该文件存在。
- **建议**：在 `server.py` 启动时检测此文件存在且非测试环境时打印显著警告或拒绝启动；在 `install.py` 生产安装流程中删除此文件。

#### [中] 速率限制可被 X-Forwarded-For 绕过

- **文件**：`backend/server.py:617-657`
- **问题**：`_get_client_ip()` 在配置了 `STUDIO_TRUSTED_PROXIES` 时，直接取 `X-Forwarded-For` 第一个值作为客户端 IP，未做 IP 格式校验。攻击者可在 XFF 中填入每次不同的随机字符串，使每个请求使用不同的 rate limit key，完全绕过每分钟 120 次的写操作限制。`_rate_windows` 字典无大小上限且不清理空窗口，长期运行可被不同 XFF 值撑大。
- **建议**：对 XFF 解析值做 `ipaddress.ip_address()` 校验；为 `_rate_windows` 增加上限或定期清理机制。

#### [中] Basic Auth 默认关闭

- **文件**：`backend/server.py:674-678`
- **问题**：当 `STUDIO_AUTH_USER` 和 `STUDIO_AUTH_PASSWORD` 均未设置时，`_authenticate()` 直接返回 True。虽然 `runtime_security.py` 强制服务绑定回环地址，但默认 localhost 部署场景下任何本机进程均可无凭证访问全部 API。
- **建议**：在首次启动时自动生成默认凭证并要求用户设置。

#### [低] GET 请求无 CSRF 防护

- **文件**：`backend/server.py:699-701`
- **问题**：`_check_origin()` 在 `self.command not in MUTATING` 时直接返回，GET/HEAD 请求不校验 Origin。浏览器缓存的 Basic Auth 凭证可被跨站 GET 请求携带。由于服务默认绑定 localhost 且有 CSP 限制，实际利用难度较高。
- **建议**：对涉及敏感数据的 GET 端点（如 `/api/v2/settings`、`/api/v2/logs`）也校验 Origin。

### 2.2 SSRF 防护

#### [中] 代理模式下 SSRF 防护降级

- **文件**：`backend/source_fetcher.py:203-215`
- **问题**：当检测到本机配置了 HTTP/HTTPS 代理时，`_validate_target` 使用 `resolve=False`，不解析域名，仅拒绝显式 IP 字面量的内网地址。`http://metadata.google.internal/` 等域名形式的目标会被放行，由代理解析。如果代理本身不阻止内网访问，攻击者可借代理解析到内网/元数据地址。
- **建议**：在代理模式下仍应通过代理解析后验证最终连接 IP，或显式提示用户此信任假设。

#### [低] source_fetcher 与 secure_http 的 SSRF 拦截策略不一致

- **文件**：`backend/source_fetcher.py:165-184` vs `backend/secure_http.py:59-73`
- **问题**：`source_fetcher._resolve_public()` 在发现不安全地址时跳过该地址并继续尝试其他地址，仅当全部不安全时才拒绝。而 `secure_http.resolve_public()` 在发现任何一个不安全地址时立即抛出异常。前者更宽松，可能存在 TOCTOU 窗口。
- **建议**：统一为 secure_http 的严格策略。

#### [信息] 直连模式 SSRF 防护充分

- 直连模式下 `_is_public_ip`/`is_public_ip` 正确检查 `is_private`、`is_loopback`、`is_link_local` 等属性，覆盖 0.0.0.0、127.0.0.1、169.254.169.254、`::1` 等。
- 十进制 IP（如 2130706433）经 `socket.getaddrinfo` 解析后被正确识别。
- IPv6 映射地址 `::ffff:127.0.0.1` 的 `is_loopback` 返回 True，被拦截。
- `_PinnedHTTP(S)Connection` 固定解析 IP 并在连接后验证 `peer == ip`，有效防护 DNS rebinding。

### 2.3 SQL 注入

#### [信息] 全部 SQL 使用参数化查询，未发现注入风险

- 对所有 `conn.execute` 调用（共 20 处）进行审查，全部使用 `?` 占位符传参。
- `db.py:160` 的 `f"PRAGMA table_info({table})"` 和 `db.py:165` 的 `f"ALTER TABLE {table} ADD COLUMN {name} {ddl}"`：`table`/`name`/`ddl` 均来自代码内硬编码字典，非用户输入。
- `server.py:1250` 的 `"UPDATE projects SET " + ", ".join(f"{column}=?" ...)`：`column` 来自硬编码列名映射，用户输入仅通过 `?` 参数传入值。

### 2.4 XSS 防护

#### [中] 预览 HTML 图片 URL 缺少协议白名单

- **文件**：`web/app.js:895`；`backend/server.py:572-581`
- **问题**：`refreshPreview()` 将服务端返回的 HTML 直接赋值给 `preview.innerHTML`。`_markdown_to_wechat_html()` 的图片语法对 URL 执行了 `escape_text`（转义 `"` 为 `&quot;`），但未限制 URL 协议。攻击者可在 Markdown 中写入 `![x](javascript:...)` 或 `![x](data:text/html,...)`。本地预览受 CSP 头保护，但若 HTML 被用于其他无 CSP 保护的上下文，风险会升高。
- **建议**：在图片和链接处理中增加协议白名单校验（仅允许 http/https/data:image）。

#### [信息] escapeHtml 实现完整

- `web/app.js:51-58`：正确转义 `&`、`<`、`>`、`"`、`'` 五个字符。
- 其余 innerHTML 使用均对用户可控内容调用了 escapeHtml。
- 日志详情弹窗使用 `textContent` 而非 innerHTML，安全。

### 2.5 密钥保护

#### [中] 自制加密方案非标准，缺乏密码学审查

- **文件**：`backend/secrets_store.py:186-218`
- **问题**：`encrypt()` 使用 HMAC-SHA256 作为密钥流进行 XOR 加密，再用 HMAC 生成认证标签。Encrypt-then-MAC 顺序正确，`decrypt()` 先验证 tag 再解密，使用 `hmac.compare_digest` 防时序攻击。nonce 为 16 字节随机数，每块使用 offset 区分密钥流。但该方案是自行构造的，未经密码学社区审查。
- **建议**：替换为标准库 `cryptography.hazmat.primitives.ciphers.aead.AESGCM` 或 `ChaCha20Poly1305`。

#### [中] STUDIO_MASTER_KEY 环境变量密钥派生无 salt

- **文件**：`backend/secrets_store.py:137-139`
- **问题**：设置 `STUDIO_MASTER_KEY` 时，密钥直接为 `hashlib.sha256(raw_env.encode("utf-8")).digest()`，无 salt、无迭代。若用户设置了弱密钥，攻击者可预计算常见密码的 SHA256 进行暴力破解。`STUDIO_MASTER_PASSWORD` 使用了 PBKDF2-HMAC-SHA256 + 32 字节随机 salt + 600,000 次迭代，安全性更高。
- **建议**：对 `STUDIO_MASTER_KEY` 也增加 salt，或建议用户使用 `STUDIO_MASTER_PASSWORD`。

#### [低] DPAPI entropy 为硬编码常量

- **文件**：`backend/secrets_store.py:72,99`
- **问题**：Windows DPAPI 使用的 entropy 为硬编码字符串 `b"WeiXinGZH-AI-Studio-2.1.2"`（版本号仍为 2.1.2）。由于 DPAPI 本身绑定到当前 Windows 用户账户，风险有限。

### 2.6 输入校验

#### [信息] 路径遍历防护充分

- `server.py:1365-1366`：通过 `if ".." in Path(relative).parts` 拦截路径遍历，使用 `Path.parts` 而非字符串包含检查，可正确处理编码绕过。

#### [信息] 输入长度/类型校验全面

- `_require_bool`/`_require_int`/`_require_number`/`_require_text` 提供了严格的类型和范围校验。封面图片有 3MB Data URL 限制 + 2MB 解码后限制 + 文件签名校验。

#### [低] task_id / project_id 路径参数无格式校验

- **文件**：`backend/server.py:911,980`
- **问题**：`task_id`/`project_id` 直接从 URL 路径取值，未校验格式。虽然 SQL 查询使用参数化不存在注入，但任意字符串可传入数据库查询和日志。
- **建议**：增加格式白名单校验，如 `re.match(r"^(prj|tsk)_[a-f0-9]{16,24}$", project_id)`。

## 三、业务逻辑维度审计

### 3.1 工作流状态机

#### [中] 收尾 UPDATE 无 revision 校验，覆盖 updated_at

- **文件**：`backend/workflow.py:554-560`
- **问题**：工作流收尾的 `UPDATE projects SET status='draft', updated_at=?` 没有 `WHERE revision=?` 条件。如果在最后一次 `_conditional_project_update` 完成后、到达收尾前，用户通过 `_patch_project` 编辑了文章，此处的 UPDATE 会无条件覆盖 `updated_at`，影响列表排序与"最近编辑"语义。
- **建议**：收尾 UPDATE 增加 `WHERE id=? AND revision=?` 条件。

#### [中] mark_interrupted_tasks 不触发回滚，文章可能停留半完成状态

- **文件**：`backend/workflow.py:359-368`
- **问题**：服务重启时，`queued/running` 任务被直接标记为 `failed`，项目状态置为 `draft`，但不调用 `_rollback_to_base_revision`。对照 `_finish_error` 对 `full` 模式的 failed/timeout 会回滚到 `base_revision` 快照，重启路径绕过了这一保护。若 `full` 重试在"框架已写入、正文未生成"时被重启打断，文章将永久停留在中间态。
- **建议**：`mark_interrupted_tasks` 对 `full` 模式的中断任务调用 `_rollback_to_base_revision`。

#### [低] status 列无 DB 级 CHECK 约束

- **文件**：`backend/workflow.py:34-36`、`backend/db.py:266-284`
- **问题**：`status` 列无 CHECK 约束，状态集合仅在 Python 层校验。`_task_update` 允许任意 status 值写入。

#### [低] 取消请求与收尾竞态产生矛盾状态

- **文件**：`backend/workflow.py:348-356` 与 `workflow.py:538-561`
- **问题**：`cancel_workflow` 仅设置 `cancel_requested=1`，不修改 status。如果工作流恰好已通过最后一个 `_guard` 进入收尾事务，取消信号被忽略，任务以 `succeeded` 完成，但 `cancel_requested` 仍为 1。

### 3.2 乐观锁与并发控制

#### [中] retry_workflow 在事务外读取 project，base_revision 可能过期

- **文件**：`backend/workflow.py:285-322`
- **问题**：`project` 在 line 290 事务外读取，`base_revision` 在 line 318 使用 `project["revision"]`。若用户在此期间编辑文章（revision 升级），retry 任务会以过期 base_revision 入库，随后 `_run_workflow` 检测到 revision 不匹配，立即抛 `WorkflowConflict`。此外 line 304 的 `UPDATE projects SET status='working'` 也没有 `WHERE revision=?`，会无条件覆盖。
- **建议**：将 project 读取移入 `_START_LOCK` 事务内，并增加 revision 条件更新。

#### [中] 冲突时 blocked 不回滚，AI 框架已覆盖人工内容

- **文件**：`backend/workflow.py:211-229`
- **问题**：`_conditional_project_update` 的 SELECT-then-UPDATE 在 WAL 模式下存在窗口。虽然 `cursor.rowcount != 1` 的兜底能捕获并发修改并回滚事务，但 `WorkflowConflict` 走 `_finish_error` 的 `blocked` 分支，不回滚内容。若 `full` 重试在框架写入后、正文写入前发生冲突，文章保留新框架而无正文，且不触发回滚。
- **建议**：`blocked` 状态下也应评估是否需要回滚到 base_revision。

#### [低] 前端串行保存链在 revision_conflict 时丢弃后续 pending 字段

- **文件**：`web/app.js:856-869`
- **问题**：`flushProjectSave` 的 while 循环在 catch 到 `revision_conflict` 后 return，未把当前 fields 之外的 pending 字段重新入队。用户需手动解决冲突。

### 3.3 发布流程

#### [高] 微信草稿创建后本地 DB 写入失败产生孤儿草稿

- **文件**：`backend/server.py:425-514`
- **问题**：`_wechat_publish` 在微信侧创建草稿（line 464）后，本地事务（line 472-505）若因 DB 锁、磁盘满、进程崩溃失败，微信侧草稿已创建但本地无记录，形成孤儿草稿。用户无法通过系统发现或清理。`cursor.rowcount != 1` 的 `stale` 分支只处理了"项目被并发修改"的情况，未处理"DB 写入异常"的情况。
- **建议**：在本地 DB 写入失败时，尝试调用微信删除草稿接口进行补偿；或记录"待确认"状态供用户手动处理。

#### [中] 并发发布可产生多个微信草稿

- **文件**：`backend/server.py:391-422` 与 `425-514`
- **问题**：`_publish_snapshot` 校验 revision 后返回，到 `_wechat_publish` 的 UPDATE 之间，没有任何锁或 revision 占位。两个并发 publish 请求若都通过 snapshot 校验，都会上传封面并创建微信草稿，最终只有一个 UPDATE 成功，另一个为 stale，stale 草稿成为孤儿。
- **建议**：在 `_publish_snapshot` 中增加 revision 占位（如将 `publish_status` 设为 `syncing`），阻止并发发布。

#### [中] stale 回执无前端提示，孤儿草稿不可见

- **文件**：`backend/server.py:489-505`
- **问题**：当 `cursor.rowcount != 1` 时，仍 INSERT 一条 `status='stale'` 的回执，但项目的 `publish_status` 未更新（仍为 `not_synced`）。前端只读 `publish_status`，不会提示用户"存在一个已同步到微信但本地未生效的 stale 草稿"。
- **建议**：前端增加 stale 回执的提示与清理机制。

### 3.4 事务完整性

#### [高] _finish_error 跨三个独立事务，部分提交导致状态不一致

- **文件**：`backend/workflow.py:673-707`
- **问题**：`_finish_error` 调用三个独立的 `connect()` 上下文：`_task_update`（事务1：UPDATE tasks）、`_rollback_to_base_revision`（事务2：UPDATE projects 回滚内容）、`UPDATE projects SET status='draft'`（事务3）。若事务1成功但事务2失败，文章保留半完成内容且任务显示 failed；若事务2成功但事务3失败，文章内容已回滚但 status 仍为 `working`，文章在列表中显示为"创作中"但无法被打开编辑。
- **建议**：将三个操作合并到同一个事务中，或在事务2和事务3之间增加重试与补偿逻辑。

#### [中] _rollback_to_base_revision 的 best-effort 吞异常可掩盖回滚失败

- **文件**：`backend/workflow.py:626-670`
- **问题**：回滚失败时仅记录日志，不向上传播。`_finish_error` 的 `rolled_back` 标志在函数正常返回后被置为 True，但实际回滚未完成。用户看到事件提示"已回滚"，但文章内容仍是半完成态。
- **建议**：回滚失败时将 `rolled_back` 保持为 False，并在事件中标注"回滚失败，需人工介入"。

### 3.5 版本历史

#### [中] 回滚后 revision 与快照表不一致，破坏恢复语义

- **文件**：`backend/workflow.py:626-668`
- **问题**：回滚将项目内容恢复到 `base_revision` 的快照内容，但 revision 设为 `base_revision+1`。如果工作流在回滚前已执行了多次 `_conditional_project_update`（如框架写入升到 `base_revision+1`，正文写入升到 `base_revision+2`），版本快照表中 `base_revision+1` 的记录是框架后内容。回滚后项目 revision=`base_revision+1`，内容是 base_revision 的快照，但版本快照表 revision=`base_revision+1` 的记录是框架后内容——两者不一致。用户通过"恢复版本 base_revision+1"会得到框架后内容，而非当前项目显示的 base_revision 内容。
- **建议**：回滚时将 revision 设为 `max(existing_revision, base_revision+1)` 之后的下一个值，或在快照表中插入一条新记录标注回滚来源。

#### [中] 100 条上限可能淘汰 base_revision 快照导致无法回滚

- **文件**：`backend/db.py:656-660`
- **问题**：版本上限保留最近 100 条 by id。一次工作流可能产生 4-5 条版本，频繁重试的活跃文章可能在短时间内产生大量版本，导致早期关键版本（如 base_revision 的快照）被淘汰。`_rollback_to_base_revision` 在检测到快照缺失时仅 warning 并 return，不回滚。
- **建议**：对 `full` 重试的 base_revision 快照增加保护标记，不被 100 条上限淘汰。

### 3.6 任务重试

#### [高] preserve_body 模式重新生成框架但保留旧正文，框架与正文不一致

- **文件**：`backend/workflow.py:422-477`
- **问题**：`preserve_body` 模式下，AI 重新生成 title/summary/outline 并写入项目，但正文仍是旧正文。新框架（outline）与旧正文不匹配——正文是根据旧框架生成的，但框架已更新。后续审校基于旧正文，审校指纹也是旧正文的指纹。最终文章的框架、摘要、标题是新的，但正文是旧的，逻辑割裂。
- **建议**：`preserve_body` 模式不应重新生成框架，或应在框架更新后标注"正文需用户确认是否需要重新生成"。

#### [中] review_only 指纹基于启动时 body，与并发编辑存在窗口

- **文件**：`backend/workflow.py:442-477,539-550`
- **问题**：`review_only` 模式下，`body = project["bodyMarkdown"]` 在工作流启动时读取一次。审校和指纹都基于这个 body。若用户在审校执行期间编辑了 body（revision 升级），`_conditional_project_update` 会因 revision 不匹配抛 `WorkflowConflict`。整体安全，但 `reviewFingerprint` 写入的是旧 body 的指纹。

#### [中] from_outline 封面生成使用旧 plan，可能与新正文不一致

- **文件**：`backend/workflow.py:421-477`
- **问题**：`from_outline` 模式下，`plan` 变量在 line 421 后未被更新，后续封面生成（line 485 `plan.get("title")`）使用的仍是旧 plan，可能与新正文不一致。
- **建议**：封面生成前重新读取项目最新 title/summary。

### 3.7 资源泄漏

#### [高] ThreadPoolExecutor 无优雅关闭，服务停止时丢弃运行中任务

- **文件**：`backend/workflow.py:21-22`、`backend/server.py:1390-1403`
- **问题**：`_EXECUTOR` 是模块级全局，`server.server_close()` 不调用 `_EXECUTOR.shutdown(wait=True)`。服务停止时运行中的工作流线程被强制终止，队列中未开始的任务被丢弃。若任务正在调用外部 API（如 AI 引擎、微信 API），外部副作用可能已发生但本地未记录。
- **建议**：在 `server.server_close()` 前调用 `_EXECUTOR.shutdown(wait=True, cancel_futures=True)`，并在 shutdown 前设置全局停止标志让运行中的 `_run_workflow` 尽快退出。

#### [中] _QUEUE_SLOTS 的 release 依赖 callback，异常路径可能泄漏

- **文件**：`backend/workflow.py:119-127`
- **问题**：`_EXECUTOR.submit` 成功后、`add_done_callback` 注册前，若 future 被取消，callback 不会执行，slot 永久泄漏。当前代码不会触发此路径，但缺乏防御性编程。
- **建议**：使用 try/finally 包裹 future 生命周期，或在 callback 中增加异常处理。

#### [中] WAL checkpoint 线程无优雅停止接口

- **文件**：`backend/db.py:81-154`
- **问题**：`_wal_checkpoint_stop` Event 存在但从未被 set。线程是 daemon，进程退出时被杀。测试场景中多次 `init_db` 靠 `is_alive()` 检查避免重复启动，但无法主动停止。
- **建议**：在 `server.server_close()` 中调用 `_wal_checkpoint_stop.set()`。

#### [低] _rate_windows 字典无 IP 维度清理

- **文件**：`backend/server.py:615`
- **问题**：窗口内旧条目会被 popleft 清理，但 IP 维度的字典 key 永不清理。直连模式下大量唯一 IP 会导致缓慢内存增长。

## 四、代码质量维度审计

### 4.1 异常处理

#### [高] init_db 迁移失败路径存在双重 close 与吞没异常

- **文件**：`backend/db.py:516-535`
- **问题**：except 块内已 `conn.close()`（527 行），finally 块又 `conn.close()`（533 行），形成双重关闭。两处 `except Exception: pass` 完全吞没了迁移日志写入失败和关闭失败，使迁移故障诊断信息丢失。
- **建议**：移除 except 块内的 `conn.close()`，仅保留 finally 块关闭；将 `pass` 改为 `logging.warning`。

#### [高] logger_config emit() 静默吞没所有异常

- **文件**：`backend/logger_config.py:102-103`
- **问题**：日志系统自身的任何异常都被 `except Exception: pass` 静默吞没。如果日志写入持续失败，系统会"无声"丢失全部日志，运维无法察觉。
- **建议**：将 `except Exception: pass` 改为 `self.handleError(record)`。

#### [中] HTML 解析异常被静默吞没

- **文件**：`backend/source_fetcher.py:636-639`
- **问题**：HTML 解析失败被完全吞没，没有日志记录。若解析器因畸形 HTML 崩溃，开发者无法知晓解析失败的具体原因和频率。
- **建议**：增加 `logger.warning` 记录解析异常。

#### [中] 内容安全检测失败时 fail-open

- **文件**：`backend/content_security.py:58-60`
- **问题**：微信内容安全 API 调用失败时返回 `safe: True`（放行）。风险内容可能在检测不可用时直接通过。应在审校结果中明确标注"检测不可用"而非"通过"。

### 4.2 资源管理

#### [中] secure_http 和 source_fetcher 的 finally 中 conn 可能未定义

- **文件**：`backend/secure_http.py:141-145`、`backend/source_fetcher.py:319-323`
- **问题**：`conn` 在循环体内赋值，若构造函数在赋值前抛异常，`conn` 未定义。finally 中的 `conn.close()` 会触发 `NameError`（被 except 吞没）。
- **建议**：初始化 `conn = None` 并在 finally 中加 `if conn:` 判断。

### 4.3 错误恢复

#### [中] mark_interrupted_tasks 不记录中断事件

- **文件**：`backend/workflow.py:359-368`
- **问题**：服务重启后将 queued/running 任务标记为 failed，但没有写入 `task_events` 表记录中断事件。用户在任务诊断页面只能看到状态变为 failed，看不到"服务重启导致中断"的事件记录。
- **建议**：在 mark_interrupted_tasks 中调用 `_event()` 记录中断原因。

### 4.4 日志覆盖

#### [中] 多处 except Exception: pass 无日志记录

- `backend/db.py:525-526`：迁移日志写入失败无日志
- `backend/db.py:534-535`：连接关闭失败无日志
- `backend/source_fetcher.py:322-323`：HTTP 连接关闭失败无日志
- `backend/secure_http.py:144-145`：同上
- `backend/source_fetcher.py:638-639`：HTML 解析失败无日志

#### [中] 500 错误返回 repr(exc) 可能泄露内部信息

- **文件**：`backend/server.py:783-785`
- **问题**：`repr(exc)` 可能包含敏感路径、SQL 语句或内部变量名。本地部署场景风险较低，但仍不规范。
- **建议**：生产模式下返回通用错误信息，仅在后端日志中记录完整 repr。

### 4.5 代码重复

#### [高] _PinnedHTTPConnection/is_public_ip/resolve_public 完全重复

- **文件**：`backend/secure_http.py:28-73` vs `backend/source_fetcher.py:133-184`
- **问题**：`_PinnedHTTPConnection`/`_PinnedHTTPSConnection` 和 `is_public_ip`/`resolve_public` 在两个文件中几乎一字不差地重复实现，约 80 行重复代码。
- **建议**：抽取为公共模块（如 `net_security.py`）。

#### [中] 封面 data URL 解析逻辑重复且安全级别不一致

- **文件**：`backend/server.py:167-190`（含 magic bytes 校验）、`backend/wechat_api.py:444-454`（无 magic bytes 校验）、`verify_external_links.py:84-93`（仅签名检测）
- **问题**：`wechat_api.py` 的解析缺少 server.py 中的 magic bytes 一致性校验，存在安全隐患。
- **建议**：抽取为公共函数，统一包含 magic bytes 校验。

#### [中] VERSION 硬编码在 5 个文件中

- `backend/server.py:63`、`verify_browser_service.py:21`、`verify_capacity.py:24`、`verify_external_links.py:21`、`verify_windows_dpapi.py:15`
- **建议**：集中到单一 `version.py` 或 `__version__` 模块。

### 4.6 类型安全

#### [中] 多处环境变量 int/float 转换无异常保护

- `backend/wechat_api.py:261-263`：`float(os.environ.get(...))` 无 try/except
- `backend/logger_config.py:18`：`int(os.environ.get(...))` 无 try/except
- `backend/workflow.py:24-32`：7 个 `int()` 调用均无 try/except
- `backend/ai_engine.py:49`：`int(config.get("maxTokens", 4096))` 无 try/except
- `backend/start.py:19`：`int(os.environ.get("STUDIO_PORT", "5000"))` 无 try/except
- **问题**：任一环境变量设为非数字会导致模块导入失败或服务启动崩溃，错误信息为 Python traceback 而非友好提示。
- **建议**：添加集中式启动时配置校验函数。

### 4.7 前端代码质量

#### [中] beforeunload 定时器清理不完整

- **文件**：`web/app.js:1318-1324`
- **问题**：`beforeunload` 只清理了 `state.pollTimer`，未清理 `state.logsPollTimer`、`state.saveTimers`（Map）、`state.articleSearchTimer`。SPA 内部路由切换时这些定时器不会被清理，可能导致已销毁组件的回调执行。
- **建议**：在路由切换时统一清理所有定时器。

### 4.8 配置管理

#### [中] 无集中式启动时配置校验

- 环境变量分散在各模块顶层（模块导入时执行），没有统一的 `validate_config()` 函数在启动时校验所有环境变量的类型和范围。
- **建议**：在 `create_server` 或 `start.py` 中增加集中式校验。
