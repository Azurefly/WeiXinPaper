# 2.1.4 全链路日志可观测性评估与开发计划

**文档版本**：v2.0（修订版）
**日期**：2026-07-24
**目标状态**：系统全链路日志化改造与前端可视化面板开发规范

---

## 1. 概述与背景

在当前的微信公众号 AI Studio 系统中，抓取（`source`）、计划（`outline`）、正文（`draft`）、审校（`review`）及快照发布（`publish`）的整个闭环流水线已具备高度完备的业务事件（`task_events`）记录能力。然而，系统在标准控制台日志打印（Standard Output/Logger）以及 Web UI 端的实时观测能力上存在明显短板：

- **系统级日志缺失**：底层模块发生网络请求超时、第三方大模型响应异常或报错 Traceback 时，没有记录到标准日志系统（Standard Logger），导致运维调试困难。
- **UI 缺失排查入口**：前端界面缺乏集中式的控制台与日志查看面板，用户在创作失败或微信发布异常时无法即时直观获取失败详情。

本文档详细评估全链路日志缺失问题，并设计全栈增强的开发计划。

---

## 2. 全链路日志审计与缺失分析

| 闭环链路环节 | 业务事件表 (`task_events`) | 系统标准 Logger | 关键日志缺失点评估 |
|---|---|---|---|
| **来源抓取 (`source`)** | 已记录开始/完成/跳过事件 | 完全缺失 | `backend/source_fetcher.py` 无 `logging` 输出；网页抓取超时、防 SSRF 拦截及 HTTP 错误无堆栈。 |
| **框架计划 (`outline`)** | 已记录开始/完成/跳过事件 | 完全缺失 | `backend/ai_engine.py` 无大模型 Prompt 消耗、请求延时与响应 Token 的系统日志。 |
| **正文生成 (`draft`)** | 已记录开始/完成/跳过事件 | 完全缺失 | 正文生成重试或异常时，无法打印原始 Error Response 和重试策略上下文。 |
| **自动审校 (`review`)** | 已记录开始/完成/跳过事件 | 完全缺失 | 审校不通过仅存储 `review_json` 最终结果，缺失校验失败原因的 Warning 日志。 |
| **人工终审与快照** | 无专用事件（乐观锁 `If-Match`） | 部分覆盖 | `backend/server.py` 仅打印 HTTP 服务启动/停止，不记录版本冲突（409 Conflict）日志。 |
| **微信同步 (`publish`)** | 记录发布回执 (`publish_receipts`) | 完全缺失 | 封面图素材上传失败或微信 API 签名认证错误时，终端无法提供调纤级 Traceback 信息。 |

### 2.1 与现有 `task_events` 系统的边界定义

系统已有 `task_events` 表记录业务事件。新增 Logger 系统与之**互补而非替代**，二者通过 `task_id` 关联但职责不同：

| 维度 | `task_events`（业务事件） | Logger（系统日志） |
|---|---|---|
| **记录内容** | 步骤转换、跳过原因、业务语义结果 | 网络耗时、HTTP 状态码、Token 消耗、异常堆栈 |
| **存储位置** | SQLite 持久化表 | 内存环形缓冲区（可选文件 fallback） |
| **生命周期** | 随项目永久保存 | 随服务重启清空（文件 fallback 除外） |
| **查看入口** | 任务时间线 UI | 日志中心面板 |
| **粒度** | 每步骤 1-3 条 | 每操作多条（含中间状态） |

## 3. 系统日志架构与开发方案

引入**内存环形缓冲区 + RESTful 日志查询 API + 前端可视化 Log Viewer** 的三层架构。

### 3.1 架构图

```
+-----------------------------------------------------------------------------------+
|                            前端 Web 界面 (web/app.js)                              |
|   +---------------------------------------------------------------------------+   |
|   |   侧边栏新增 [#logs 日志中心] 入口 (提供级别过滤 / 关键字搜索 / 自动刷新)   |   |
|   +---------------------------------------------------------------------------+   |
+------------------------------------------^----------------------------------------+
                                           | GET /api/v2/logs
+------------------------------------------v----------------------------------------+
|                            后端 HTTP 服务 (backend/server.py)                     |
|   +---------------------------------------------------------------------------+   |
|   |   路由映射: GET /api/v2/logs & Access Log 通过 Logger 输出               |   |
|   +---------------------------------------------------------------------------+   |
+------------------------------------------^----------------------------------------+
                                           | 读取 / 写入
+------------------------------------------v----------------------------------------+
|                          日志基础设施 (backend/logger_config.py)                  |
|   +---------------------------------------------------------------------------+   |
|   | RingBufferHandler (deque(maxlen=2000), threading.Lock) + StreamHandler   |   |
|   +---------------------------------------------------------------------------+   |
|         ^                           ^                           ^                 |
|         |                           |                           |                 |
|  source_fetcher.py             ai_engine.py                workflow.py            |
+-----------------------------------------------------------------------------------+
```

### 3.2 线程安全设计

系统使用 `ThreadingHTTPServer` + `ThreadPoolExecutor`（最大 6 线程并发），日志写入和读取必须线程安全：

- **写入端**：`collections.deque(maxlen=2000)` 的 `append()` 是 CPython 原子操作，无需加锁。
- **读取端**：关键字搜索和过滤需要遍历 deque，使用 `threading.Lock` 保护快照读取，避免遍历期间数据竞争。
- **实现方式**：自定义 `RingBufferHandler(logging.Handler)`，在 `emit()` 中直接 `deque.append()`，在 `query()` 中 `with lock:` 获取列表快照。

### 3.3 敏感数据脱敏策略

日志可能包含 API Key、微信 AppSecret、用户正文等敏感信息，必须脱敏：

| 敏感类型 | 脱敏规则 | 示例 |
|---|---|---|
| API Key / Bearer Token | 正则 `(?i)(bearer |sk-|api[_-]?key)[\s:=]+\S+` → 替换为 `***REDACTED***` | `Bearer sk-abc123` → `Bearer ***REDACTED***` |
| AppSecret | 调用方在写入日志前自行截断，仅记录前 4 位 | `appSecret=abcdef...` → `appSecret=abcd***` |
| 用户正文 | 仅记录长度和前 80 字符 | `body_len=3500 preview=前80字符...` |
| 微信 access_token | 正则 `access_token["\s:=]+[\w-]+` → `***REDACTED***` | `access_token=xxx` → `access_token=***REDACTED***` |

### 3.4 端点安全

日志 API 端点受现有安全机制保护：

- **Origin 校验**：复用 `_check_origin()`，仅允许 `127.0.0.1` / `localhost` 来源。
- **鉴权**：复用 `_authenticate()`，若配置了 `STUDIO_AUTH_USER` / `STUDIO_AUTH_PASSWORD` 则需 Basic Auth。
- **stack 字段**：对外暴露时保留完整堆栈（本地单机部署场景，不对外网开放）。

### 3.5 日志级别与配置

通过环境变量控制日志行为：

| 环境变量 | 默认值 | 说明 |
|---|---|---|
| `STUDIO_LOG_LEVEL` | `INFO` | 全局日志级别（DEBUG/INFO/WARNING/ERROR） |
| `STUDIO_LOG_BUFFER_SIZE` | `2000` | 环形缓冲区最大条数 |
| `STUDIO_LOG_FILE` | （空） | 若设置，额外写入指定文件（可选持久化） |

## 4. 三阶段开发实施计划

### 阶段一：后端日志基础设施改造（Backend Foundation）

#### 目标
创建标准 Logger 模块，配置内存环形缓冲区，改造核心业务模块的日志输出。

#### 交付任务
1. **新建日志配置文件 `backend/logger_config.py`**：
   - 自定义 `RingBufferHandler(logging.Handler)`，使用 `collections.deque(maxlen=N)` 实现环形队列，`threading.Lock` 保护读取。
   - 通过 `LoggerAdapter` 注入 `task_id`，格式为：`[%(asctime)s] [%(levelname)s] [%(name)s] [task:%(task_id)s] %(message)s`。
   - 无 `task_id` 的请求（健康检查、静态资源）该字段显示为 `-`。
   - 同时输出到 `StreamHandler`（stdout）和 `RingBufferHandler`，可选 `FileHandler`。
   - 提供 `redact_sensitive(text)` 函数实现敏感数据脱敏。
2. **模块日志嵌入**：
   - `backend/source_fetcher.py`：增加抓取开始、防 SSRF IP 校验通过/拦截、网页解析耗时与 HTTP 状态日志。
   - `backend/ai_engine.py`：增加 AI API 请求耗时、响应 Token 统计、重试警告与失败错误日志。
   - `backend/workflow.py`：在流水线各阶段转换时打印任务上下文，在 Exception 捕获点补充 `logger.exception()` 堆栈输出。
3. **HTTP 服务 Access Log**：
   - 改造 `backend/server.py` 的 `log_message()`，通过 Logger 输出每个 API 请求的客户端 IP、路径、状态码和耗时（ms）。
   - Access Log 与业务日志统一进入环形缓冲区，通过 `module=access` 区分。

---

### 阶段二：后端日志 RESTful API 实现（Log Query API）

#### 目标
对外暴露轻量级日志查询接口，支持按级别与关键字筛选。

#### 交付任务
1. **新增 API 路由 `GET /api/v2/logs`**：
   - 支持 Query 参数：`level` (ALL/INFO/WARN/ERROR)、`q` (关键字搜索)、`limit` (默认 100，最大 1000)、`since` (ISO 时间戳过滤)。
   - 返回标准 JSON 结果结构：
     ```json
     {
       "total": 150,
       "logs": [
         {
           "timestamp": "2026-07-24T15:30:00.123Z",
           "level": "ERROR",
           "module": "ai_engine",
           "task_id": "tsk_98234",
           "message": "AI API request timeout after 90s",
           "stack": "Traceback (most recent call last)..."
         }
       ]
     }
     ```
2. **新增任务专属日志路由 `GET /api/v2/tasks/{id}/logs`**：
   - 路由风格对齐现有代码（Python f-string 风格 `{id}` 而非 Express.js 风格 `:id`）。
   - 自动过滤 `task_id` 匹配的日志条目。
3. **自动化测试覆盖**：
   - 编写 `tests/test_logs_api.py`，验证：
     - 日志写入后在 API 中可查到。
     - 缓冲区上限行为（超过 2000 条后旧条目自动淘汰）。
     - 级别过滤与关键字搜索准确度。
     - `since` 时间戳过滤。
     - 任务专属日志路由。
     - 敏感数据脱敏生效。
     - Origin 校验与鉴权拦截。
   - 现有 45 个测试必须全部通过（回归门禁）。

---

### 阶段三：前端 Web 界面日志可视化查看面板（Log Viewer）

#### 目标
在单页应用（SPA）中增加可视化日志面板，用户无需进入服务器后台即可直观查看系统日志。

#### 交付任务
1. **扩展路由与导航 (`web/app.js`)**：
   - 在 `ROUTES` 对象中添加 `logs` 项：`logs: { label: '日志', icon: '📋', title: '系统日志中心' }`。
   - 侧边栏导航添加"日志"入口。
2. **渲染 Log Viewer 界面结构**：
   - 顶部控制栏：日志级别下拉切换（`ALL`/`INFO`/`WARN`/`ERROR`）、防抖搜索框、开启/暂停轮询刷新开关、一键导出按钮。
   - 轮询策略：对齐现有系统自适应频率——活跃任务时 3 秒、空闲时 15 秒。
   - 主体日志列表：终端样式设计，ERROR 绯红、WARN 橙黄、INFO 青绿、DEBUG 灰色。
   - 展开/收起堆栈：带 `stack` 字段的 ERROR 日志提供折叠面板。
3. **样式美化 (`web/styles.css`)**：
   - 补充 `.log-viewer`、`.log-row`、`.log-row-error`、`.log-row-warn`、`.log-row-info`、`.log-stack-trace` 样式类。

## 5. 验收与门禁标准

1. **功能完整度**：每个闭环环节（source/outline/draft/review/publish）的 ERROR 级别异常在 `GET /api/v2/logs` API 中可查到对应记录，且包含 `stack` 堆栈信息。
2. **性能无衰减**：内存环形日志限制在 2,000 条以内，内存占用不超过 10 MB，`GET /api/v2/logs` API 响应时间小于 50 ms（含关键字搜索）。
3. **线程安全**：多线程并发写入下无数据竞争，读取操作返回一致快照。
4. **敏感数据保护**：API Key、Bearer Token、微信 access_token 在日志输出中被脱敏。
5. **自动化测试**：`pytest tests/test_logs_api.py` 全部通过，现有 45 个测试零回归。
